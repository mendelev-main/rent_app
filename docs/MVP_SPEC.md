# MVP Specification

## 1. Product

Rent App — Telegram Mini App + Telegram Bot для краткосрочной аренды жилья между собственниками и гостями.

## 2. Роли

Один Telegram-пользователь может использовать обе роли:

- **Гость** — ищет и бронирует жильё.
- **Собственник** — размещает и управляет объектами.

На первом входе пользователь выбирает основной сценарий: **Снять** / **Сдать**. Выбор не блокирует вторую роль навсегда.

## 3. Авторизация — реализовано

- Вход выполняется через Telegram Mini App.
- Клиент передаёт `Telegram.WebApp.initData` backend Railway.
- Backend валидирует подпись и свежесть `auth_date`.
- `initDataUnsafe` не используется как источник доверенной идентичности.
- После успешной проверки backend создаёт или обновляет пользователя в Supabase PostgreSQL по уникальному `telegram_user_id`.
- Внутренний идентификатор пользователя — UUID `public.users.id`.
- Supabase Auth для пользовательского входа в MVP не используется: доверенная идентичность приходит из Telegram и проверяется backend.
- Mini App не получает прямые привилегированные ключи Supabase и не обращается к приватным данным напрямую.

Рабочая цепочка подтверждена на production:

```text
Telegram → Mini App → Railway API → validation initData → Supabase users
```

## 4. Сценарий собственника — текущая итерация

MVP должен позволять:

1. Создать объект.
2. Загрузить несколько фотографий.
3. Указать:
   - название;
   - город;
   - адрес;
   - описание;
   - цену за сутки в BYN;
   - максимальное количество гостей;
   - время заезда / выезда;
   - основные удобства;
   - правила проживания.
4. Сохранить объект как черновик.
5. Опубликовать / снять с публикации.
6. Просматривать календарь объекта.
7. Вручную блокировать даты.
8. Смотреть входящие заявки на бронирование.
9. Подтверждать или отклонять заявку.

### 4.1 Модель объекта

`properties` хранит объект и обязательно связан с `users` через `owner_id`.

Статусы объекта:

- `draft` — черновик;
- `published` — виден гостям;
- `archived` — снят с публикации/архивирован.

Базовые поля первой версии: `title`, `city`, `address`, `description`, `price_per_night`, `currency`, `max_guests`, `amenities`, `house_rules`, `check_in_time`, `check_out_time`.

Валюта первого MVP — BYN. Цена должна быть больше нуля. Максимальное количество гостей — от 1 до 50.

### 4.2 Фотографии объекта

Метаданные фотографий хранятся в `property_photos`, сами файлы — в Supabase Storage bucket `property-photos`.

- Поддерживаем JPEG, PNG и WebP.
- Максимальный размер одного файла — 10 MB.
- У фотографии есть порядок сортировки и признак обложки.
- Публичная выдача опубликованных фотографий допустима, но загрузка/изменение выполняются только через доверенный backend.
- Клиенту не выдаются server-side Storage credentials.

### 4.3 Безопасность данных

`users`, `properties` и `property_photos` находятся в exposed-схеме `public`, поэтому RLS включён на всех трёх таблицах. В текущей архитектуре Mini App работает с ними только через Railway backend; публичные RLS policies намеренно не создаются. Backend использует серверное PostgreSQL-соединение.

## 5. Сценарий гостя

MVP должен позволять:

1. Просматривать опубликованные объекты.
2. Выбирать город.
3. Выбирать даты заезда и выезда.
4. Указывать количество гостей.
5. Видеть только доступные для выбранных дат варианты.
6. Открывать карточку объекта с фотографиями и информацией.
7. Отправлять заявку на бронирование.
8. Смотреть статус своих заявок / броней.
9. После появления доступного контакта переходить к общению через Telegram.

## 6. Бронирование

Базовые статусы:

- `pending`
- `confirmed`
- `rejected`
- `cancelled`
- `completed`

Для MVP бронь создаётся как заявка `pending` и требует подтверждения собственником.

`confirmed` бронь блокирует соответствующие даты.

## 7. Календарь

Источник истины — backend/database Rent App.

Недоступность даты может появиться из:

- подтверждённой брони Rent App;
- ручной блокировки владельца;
- импортированной внешней блокировки календаря.

UI не является механизмом защиты от двойного бронирования. Финальная проверка доступности происходит на сервере внутри транзакционной операции создания/подтверждения брони.

## 8. Telegram Bot

В MVP бот используется для уведомлений:

- новая заявка собственнику;
- заявка подтверждена;
- заявка отклонена;
- бронь отменена;
- напоминания можно добавить после базового MVP.

Бот и Mini App используют одну пользовательскую модель.

## 9. Общение

На первом MVP отдельный чат внутри приложения не создаётся.

После разрешённого продуктом момента Mini App показывает действие **«Написать»**, ведущее в Telegram.

Это решение должно быть реализовано так, чтобы позже можно было добавить проксируемый чат или скрытие прямого контакта без переделки модели бронирований.

## 10. Внешние календари

Архитектура предусматривает iCalendar (`.ics`) интеграции.

Первая версия интеграционного слоя должна поддерживать концепции:

- внешний источник календаря;
- импорт занятых периодов;
- экспорт календаря Rent App;
- журнал последней синхронизации;
- дедупликация внешних событий.

Avito и Kufar рассматриваются как конкретные адаптеры только после проверки их актуальных возможностей экспорта/импорта календарей.

## 11. Инфраструктура — зафиксировано

- GitHub `mendelev-main/rent_app` — исходный код и спецификация.
- `main` — production-ветка MVP.
- Railway — Node.js/Fastify backend и раздача Telegram Mini App; push в `main` запускает production deployment.
- Supabase — PostgreSQL и Storage.
- Railway подключается к PostgreSQL через `DATABASE_URL` (Session pooler).
- Telegram — идентификация пользователя и уведомления.
- Секреты хранятся только в server-side environment variables и не коммитятся в Git.

## 12. Что НЕ входит в первый MVP

- встроенная онлайн-оплата;
- выплаты собственникам;
- комиссия платформы;
- собственный real-time чат;
- рейтинги и отзывы;
- сложная модерация;
- динамическое ценообразование;
- промокоды;
- полноценная карта;
- юридическая автоматизация договоров;
- channel manager уровня профессиональных PMS.

## 13. Definition of MVP

MVP считается достигнутым, когда реальный пользователь из Telegram может пройти цепочку:

```text
Telegram
  → открыть Mini App
  → войти через Telegram
  → собственник создаёт и публикует объект
  → другой пользователь находит объект
  → выбирает свободные даты
  → отправляет заявку
  → собственник получает Telegram-уведомление
  → подтверждает
  → даты блокируются
  → гость получает уведомление о подтверждении
```

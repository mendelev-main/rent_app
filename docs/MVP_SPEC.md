# MVP Specification

## 1. Product

Rent App — Telegram Mini App + Telegram Bot для краткосрочной аренды жилья между собственниками и гостями.

## 2. Роли

Один Telegram-пользователь может использовать обе роли: **Гость** — ищет и бронирует жильё; **Собственник** — размещает и управляет объектами. На первом входе пользователь выбирает основной сценарий: **Снять** / **Сдать**. Выбор не блокирует вторую роль навсегда.

## 3. Авторизация — реализовано

- Вход выполняется через Telegram Mini App.
- Клиент передаёт `Telegram.WebApp.initData` backend Railway.
- Backend валидирует подпись и свежесть `auth_date`.
- `initDataUnsafe` не используется как источник доверенной идентичности.
- После успешной проверки backend создаёт или обновляет пользователя в Supabase PostgreSQL по уникальному `telegram_user_id`.
- Внутренний идентификатор пользователя — UUID `public.users.id`.
- Supabase Auth для пользовательского входа в MVP не используется: доверенная идентичность приходит из Telegram и проверяется backend.
- Mini App не получает прямые привилегированные ключи Supabase и не обращается к приватным данным напрямую.

Рабочая цепочка: `Telegram → Mini App → Railway API → validation initData → Supabase users`.

## 4. Сценарий собственника — текущая итерация

MVP позволяет последовательно реализовать: создание объекта, фотографии, название, город, адрес, описание, цену в BYN, число гостей, время заезда/выезда, удобства и правила; сохранение черновика; публикацию/архивирование; календарь; ручные блокировки; заявки и подтверждение/отклонение брони.

### 4.1 Модель объекта

`properties` связан с `users` через `owner_id`. Статусы: `draft`, `published`, `archived`. Базовые поля: `title`, `city`, `address`, `description`, `price_per_night`, `currency`, `max_guests`, `amenities`, `house_rules`, `check_in_time`, `check_out_time`. Валюта MVP — BYN. Цена больше нуля, число гостей 1–50.

### 4.2 Фотографии объекта

Метаданные находятся в `property_photos`, файлы — в Supabase Storage bucket `property-photos`. JPEG/PNG/WebP, до 10 MB на файл. Есть порядок сортировки и обложка. Публичная выдача опубликованных фото допустима, загрузка/изменение идут через доверенный backend; server-side credentials клиенту не выдаются.

### 4.3 Безопасность данных

`users`, `properties`, `property_photos` имеют RLS. Mini App работает с ними через Railway backend; публичные RLS policies намеренно не создаются. Каждый owner endpoint повторно валидирует Telegram `initData`, получает внутренний `users.id`, а запрос объекта всегда ограничивается `owner_id`. Переданный клиентом `owner_id` никогда не принимается как источник авторизации.

### 4.4 Owner Property API — реализовано

Backend предоставляет авторизованные операции:

- `POST /api/owner/properties/list` — список только своих объектов;
- `POST /api/owner/properties` — создание своего объекта со статусом `draft`;
- `POST /api/owner/properties/:id/get` — получение своего объекта;
- `POST /api/owner/properties/:id` — редактирование своего объекта.

Каждый запрос передаёт свежий Telegram `initData`. Backend валидирует пользователя, выполняет create/update `users`, затем использует серверный UUID пользователя как `owner_id`. Входные данные объекта проверяются backend до записи в PostgreSQL.

## 5. Сценарий гостя

MVP: опубликованные объекты; выбор города, дат и гостей; выдача только доступных вариантов; карточка объекта; заявка на бронирование; статусы броней; переход к разрешённому общению через Telegram.

## 6. Бронирование

Статусы: `pending`, `confirmed`, `rejected`, `cancelled`, `completed`. Заявка создаётся как `pending`, собственник подтверждает её. `confirmed` блокирует даты.

## 7. Календарь

Источник истины — backend/database Rent App. Недоступность возникает из подтверждённой брони, ручной блокировки или импортированной внешней блокировки. UI не защищает от двойного бронирования: финальная проверка должна выполняться сервером транзакционно.

## 8. Telegram Bot

MVP-уведомления: новая заявка собственнику, подтверждение, отклонение, отмена. Напоминания — после базового MVP. Бот и Mini App используют одну пользовательскую модель.

## 9. Общение

В первом MVP собственного чата нет. После разрешённого продуктом момента действие **«Написать»** ведёт в Telegram. Архитектура должна позволить позже добавить проксируемый чат/скрытие контакта без переделки бронирований.

## 10. Внешние календари

Предусмотрен iCalendar (`.ics`) слой: внешний источник, импорт занятых периодов, экспорт Rent App, журнал синхронизации, дедупликация. Avito и Kufar подключаются как адаптеры только после проверки их актуальных возможностей.

## 11. Инфраструктура — зафиксировано

- GitHub `mendelev-main/rent_app` — код и спецификация.
- `main` — production-ветка MVP.
- Railway — Fastify backend + Mini App; push в `main` запускает deployment.
- Supabase — PostgreSQL + Storage.
- Railway → PostgreSQL через `DATABASE_URL` Session pooler.
- Telegram — идентификация и уведомления.
- Секреты только в server-side environment variables.

## 12. Что НЕ входит в первый MVP

Встроенная оплата, выплаты, комиссия, собственный real-time чат, рейтинги/отзывы, сложная модерация, динамическое ценообразование, промокоды, полноценная карта, юридическая автоматизация и профессиональный PMS/channel manager.

## 13. Definition of MVP

`Telegram → Mini App → Telegram auth → собственник создаёт/публикует объект → гость находит его → выбирает свободные даты → заявка → Telegram-уведомление собственнику → подтверждение → блокировка дат → уведомление гостю`.
